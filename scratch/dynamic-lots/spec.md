# Спека: витрина и лоты как клиентская проекция БД

Status: ready-for-agent

## Problem Statement

Сейчас карточки лотов и страницы лотов запекаются в HTML на этапе сборки сайта (SSG): набор
карточек в «Бирже» и существование страницы `/lots/<slug>/` определяются тем, что было в БД
в момент `npm run build`. Само содержимое карточки (владелец, цена) уже обновляется в рантайме
из БД, но чтобы **новый лот** появился в витрине и получил страницу, нужно пересобрать и
задеплоить сайт (`npm run deploy`).

Из-за этого публикация контента связана с релизом кода: добавила лот в БД — на проде его нет,
пока не сделан деплой. Хотим: лот появился в БД → он сразу виден и покупаем на проде, без деплоя.

## Solution

Витрина и страница лота строятся в браузере из БД, а не из запечённого HTML.

- Витрина `/lots/` приезжает как каркас без карточек; клиент читает каталог из БД и рисует сетку,
  дальше Realtime добавляет/убирает/обновляет карточки.
- Страница лота — один маршрут `/lot/?id=<slug>`; клиент читает `id`, тянет состояние лота из БД
  и рисует карточку и историю перепродаж. Работает для лота, которого не было на билде.
- Билд больше не ходит в БД: сборка перестаёт зависеть от доступности Supabase (но по-прежнему
  требует `PUBLIC_SUPABASE_*`, чтобы в бандл уехала конфигурация).
- Публикация контента = только `just lots-sync`. Деплой нужен лишь для изменений кода.

Почему query-параметр: GitHub Pages — статический хостинг и не может отдать код 200 по пути,
для которого нет файла. Единственный способ дать **новому** лоту настоящую страницу без пересборки —
унести идентификатор лота в query на существующий файл.

## User Stories

1. Как Чатерс, я хочу видеть витрину с актуальным списком лотов из БД, чтобы каждая существующая
   карточка была доступна.
2. Как Чатерс, я хочу, чтобы новая карточка появлялась в витрине сама, как только лот появился
   в БД, чтобы не ждать деплоя.
3. Как Чатерс, я хочу, чтобы карточка исчезала из витрины, когда лот удалён из БД, чтобы витрина
   не показывала мёртвые лоты.
4. Как Чатерс, я хочу, чтобы владелец и цена на карточке обновлялись вживую при чужом перекупе,
   чтобы видеть актуальную цену перед покупкой.
5. Как Чатерс, я хочу открывать страницу любого лота по адресу `/lot/?id=<slug>`, в том числе лота,
   появившегося после последнего деплоя.
6. Как Чатерс, я хочу, чтобы на странице лота были видео, владелец, цена и заголовок лота.
7. Как Чатерс, я хочу видеть на странице лота историю перепродаж, чтобы понимать его судьбу.
8. Как Чатерс, я хочу перейти на страницу лота кликом по карточке витрины.
9. Как Чатерс, я хочу видеть бейдж «ТВОЙ» и неактивную кнопку «Твой привет» на своём лоте.
10. Как Чатерс, я хочу видеть секцию «Мои приветы» со всеми своими лотами, чтобы быстро вернуться
    к ним.
11. Как Чатерс, я хочу видеть 4 случайных привета на главной, выбранных из свежего каталога.
12. Как Чатерс, я хочу покупать лот и с витрины, и со страницы лота — механика покупки не меняется.
13. Как Чатерс, я хочу, чтобы кнопка покупки показывала живую цену следующего перекупа.
14. Как Чатерс, я хочу, чтобы при недоступной БД витрина и страница лота не падали, а показывали
    понятное состояние (пусто/ошибка/загрузка).
15. Как Чатерс, я хочу, чтобы при возврате на вкладку данные обновлялись.
16. Как Чатерс, я хочу, чтобы заголовок вкладки на странице лота был названием лота.
17. Как Чатерс, я хочу, чтобы открытие `/lot/?id=` с несуществующим или пустым id показывало
    «лот не найден», а не пустую страницу.
18. Как Стример, я хочу публиковать новый лот одной командой `just lots-sync` и сразу видеть его
    на проде, без деплоя.
19. Как Стример, я хочу, чтобы правка ника/видео лота в манифесте и синк применялись на проде сразу.
20. Как Стример, я хочу, чтобы сборка падала явно, если `PUBLIC_SUPABASE_*` не заданы, чтобы
    не задеплоить молча сломанное приложение.
21. Как Стример, я хочу, чтобы сборка не зависела от доступности БД, чтобы гейт не краснел из-за
    сетевых проблем с Supabase.

## Implementation Decisions

- **Витрина — каркас + клиентский рендер.** HTML витрины не содержит карточек. Клиент читает
  каталог существующим швом `fetchLotCatalog(uid)` (модуль каталога лотов) и рендерит сетку;
  подписка `subscribeLots` перерисовывает по INSERT/UPDATE/DELETE. Реализуем reconcile набора
  (создание/удаление узлов) поверх сегодняшнего «патча» существующих узлов.
- **Один источник разметки карточки.** Разметка карточки живёт в `LotCard` и рендерится в
  `<template>`; клиент клонирует шаблон и заполняет поля. HTML-строкой в JS разметку не дублируем.
- **Страница лота — один маршрут `/lot/`.** Статический каркас с плейсхолдерами; клиент читает
  `?id=`, тянет `fetchLotState(slug, uid)` и историю (`fetchSharedHistory`), заполняет карточку.
  `document.title` обновляется из названия лота.
- **Клиентские помощники выносим из компонентов в общие модули**, чтобы их использовали и SSR-компонент,
  и клиентский рендер:
  - помощник заголовка с эмоутами (на базе существующего `splitTitleEmotes`, чистая функция — годится
    для клиента);
  - помощник инлайн-видео: вывести источники (webm/mp4/постер) из `video_url`, инициализировать
    видео-корень и проиграть его (сейчас это локальный скрипт внутри компонента, недоступный
    клиентскому рендеру).
  - `LotVideo` перестаёт прятать корень при отсутствии видео: корень рендерится всегда, а наличие
    видео определяется по data-атрибутам, чтобы клон шаблона был пригоден для заполнения.
- **Кнопка покупки.** Передача данных покупки остаётся через `data-buy-lot*`; модалка покупки уже
  слушает клики делегированием на `document`, поэтому динамически добавленные кнопки работают без
  изменений.
- **Главная — 4 случайных привета из свежего каталога**, выбираются в браузере, а не на билде.
- **Удаляем SSG-путь:** маршрут `[id]` и `getStaticPaths`, `fetchCatalogLots`, `buildEnv` и связанные
  типы/мапперы, если перестанут использоваться; билд-рандом на главной.
- **Проверка конфигурации на билде.** Явное падение при отсутствии `PUBLIC_SUPABASE_*` переносится
  из модуля каталога на этап сборки (конфиг/пре-билд скрипт) — правило «гейт красный — деплоя нет»
  сохраняется, но без похода в БД.
- **Механика экономики не меняется:** цена, перекуп, комиссия, пауза — источник истины по-прежнему БД;
  клиент только показывает.

## Testing Decisions

- В репозитории нет тест-фреймворка и тест-скрипта; автотесты в этом изменении не вводим.
- Хороший тест здесь проверял бы внешнее поведение: «даёшь каталог → получаешь набор карточек» и
  «даёшь slug → получаешь состояние лота». Это чистые мапперы каталога (`toLotState`) — на них и
  можно будет опереться, когда появится раннер.
- Проверка сейчас — вручную по релизному циклу репозитория: `npm run build` (гейт) + preview и
  `agent-browser` (см. `docs/agents/shipping.md`). Сценарии: лот есть на билде; лот добавлен после
  билда; лот удалён; чужой перекуп обновляет цену вживую; `/lot/?id=` с несуществующим id.
- Сегодняшние «тесты» — это pre-commit (`eslint` + `prettier`); стиль обязателен к прохождению.

## Out of Scope

- SSR и переезд с GitHub Pages на хостинг с сервером.
- Автодеплой через GitHub Actions (ортогонально, отдельное решение).
- Поддержка старых адресов `/lots/<slug>/` и редиректы с них.
- Первый экран/SEO/превью-ссылки без JS и для поисковиков.
- Клиентский роутинг между витриной и страницей лота (переходы обычные).
- Смена механики экономики (цена/комиссия/пауза/гамба).
- UI удаления лотов: реакция на DELETE — best-effort, инструмента удаления нет.
