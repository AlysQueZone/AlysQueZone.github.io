# Намерение покупки — один типизированный слот: `data-buy-intent` и `src/lib/buy-intent.ts`

Намерение «купить этот Лот» передаётся от кнопки к модалке покупки одним JSON-слотом `data-buy-intent`; форма — тип `BuyIntent` (`slug`, `title`, `price`, `owner`, `video`), запись/чтение слота и обновление цены на кнопке — только через `src/lib/buy-intent.ts`. Там же — одно правило доступности `buyAvailability(intent, balance)` («не хватает Пивкойнов»: цена известна и баланс меньше) и показ неизвестной цены `formatStaged` («…»). `price: null` значит «следующая цена N неизвестна»: кнопка показывает «…», гейт не применяется — цену всё равно считает сервер. Пустой атрибут — слот до заполнения: кнопка без намерения модалку не открывает.

Свой лот (`mine`) — состояние поверхности, не намерения: карточка знает его из `LotState` и гасит кнопку до клика — модалка свои лоты не открывает. Тексты кнопок остаются у поверхностей (витрина и модалка говорят по-разному); общим является состояние, не копирайт. Серверный гейт (`insufficient funds`) — последняя инстанция; клиентское правило лишь гасит кнопку заранее.

## Considered Options

- **Шесть data-атрибутов с типизированным доступом** (`data-lot-title`, `data-lot-price`, …): имена и разбор остаются размазаны по DOM — переименование поля молча ломает читателя; запись неатомарна.
- **Реестр в WeakMap** (кнопка → намерение, без DOM): тип честнее, но состояние не видно в инспекторе, а клонирование узла (шаблон карточки витрины) теряет намерение; для отладки живого DOM хуже.
- **Модуль кнопки целиком** (включая тексты и `disabled`): у витрины и модалки разные формулировки и разные жизненные циклы (пауза/лимит/гость) — общий модуль потянул бы параметры вместо ясности.
